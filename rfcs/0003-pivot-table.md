# RFC 0003 · Pivot 宽表与折线图共享结果

草案。跟踪 [DARI #12](https://github.com/hh9527/dari/issues/12)，沿用 [RFC 0002](0002-remote-pivot.md) 的二维结果契约。

## 用法

设 `hourly` 是远端查询中以 `pivot({index: $.hour, columns: $.device, values: $.rate, max_rows: 48, max_columns: 12})` 结束的数据节点。

```dari
answer tree! { Answer [
    Table(data = hourly, spec = {title: "各设备逐小时发送速率"}),
    LineChart(data = hourly, spec = {title: "各设备发送速率趋势"})
] };
```

`Table` 以时间索引为首列，为每个设备键生成一列。 `LineChart` 以同一索引为横轴，为每个设备键生成一条线。两者的单元格或点值都取自 `values`。动态列由 Pivot 决定，首版通过 `spec.title` 设置表题。

## 检查与执行

`check` 对 Pivot 表格应用 110 个索引行和 12 个数据列的预算，索引列另计。预算依据静态结果契约检查，超出时定位到表格的 `data` 引用。执行阶段沿用 RFC 0002 的轴和坐标校验，校验通过后按数据节点缓存结果。表格与折线图读取同一次执行的结果，包括跨 Answer 和 Report 的引用。

## 创作时确定序列范围

用于展示的 Pivot 必须在 `check` 阶段证明列键数量有界。编译器将证明得到的上界与稿件中的 `max_columns` 和组件预算比较。预算声明只表达期望上限，证明来自模型发布的有限键域、显式选择的有限键集合，或在整个查询窗口上执行的有界键选择。运行时校验负责验证返回结果遵循已检查的计划。

当列键域最多有 13 项而预算为 12 时，即使当前样本恰好只有 12 项，`check` 也在 `pivot` 的列配置处报错，并给出证得的上界与预算。若题意指定业务子集，作者用业务条件筛选，或显式列出该子集的键。若题意要求取前 N 个键，稿件须在整个查询窗口内按每个键聚合排名指标，用 `order_by(...) |> take(N)` 确定键集合，并指定稳定的并列次序。所有索引行共用这组键。仅有列预算时，作者需要从题意确定取舍规则，必要时向用户确认。需要展示全部类别时，稿件可以为多张图表声明各自可证明有界的类别组。

封闭枚举的成员数就是列数上界。若上界符合预算，直接保留所有实际出现的成员。显式业务筛选得到的有界集合也可直接使用。只有按排名取子集时才要求排序规则。对于显式键集合，编译器证明其数量上界，作者根据题意确定业务范围。SQLite 首版也支持 `rank_columns: [desc(sum($.rate)), asc($.device)]`。对完整窗口内同一列键的可加指标求和，并以列键的稳定存储顺序打破并列。远端用 `max_columns` 作为键选择上界，随后仅打包选中键的坐标。全空指标的列键排在有值的列键之后。

全表表头与折线序列使用同一组完整列键和稳定顺序。列身份按业务类型区分，展示标签冲突时应消歧，保留各列与序列的对应关系。稀疏坐标和空指标在表格中留空，在折线中留出缺口。实测零保留为零。空结果沿用组件的 `allow_no_data` 约定。

## 回执

页面和报告中的表格采用宽表。表格数据回执使用宽 CSV，包含索引列和实际出现的全部动态列。折线图回执沿用长 CSV，每条记录包含索引、列键和指标。两种回执按坐标核对值，处理 CSV 引号、逗号和换行时沿用现有转义规则。

## 验收

- 同一稿件通过 `check`，`submit` 只调用一次远端执行器
- 48 × 12 的完整样本得到 48 行、13 列的页面表格与宽 CSV，折线图有 12 条序列，长 CSV 包含 576 个数据行
- 按索引和列键逐项核对表、图及两份回执中的 576 个值
- 最后一小时才出现的设备仍进入全表表头，两份输出的列键顺序一致，缺测留空且实测零显示为零
- 111 个索引行或 13 个数据列的声明预算在 `check` 阶段触发对应诊断
- 仅用折线图的既有 Pivot 稿件和普通静态表格用例继续通过
- 已知 13 个可能键但预算为 12 时，分别以实际出现 12 个与 13 个键的样本验收，两份稿件都在 check 阶段得到相同的上界诊断
